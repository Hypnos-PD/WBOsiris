# 牌桌界面改造计划（引擎 ↔ 界面契约 / 交互 / 房间）

目标：手动对局能"打完一局、看得清、手感接近游戏"，并把**引擎已经支持、界面表达不了**
的能力补齐。文档里每条都标了证据（文件/命令），"必修"和"要先定方案"分开写。

范围：`web/`（React + Vite 前端）。引擎规则本身不改；只有房间生命周期那节可能牵到
`internal/server`。

## 一、引擎 ↔ 界面契约对照（现状）

引擎在 `internal/runner/simulator.go` 的 `LegalActionsFor` 里列出的合法动作，与界面能
表达的动作对比如下：

| 引擎会发 | 含义 | 界面 | 结论 |
| --- | --- | --- | --- |
| `play` | 本体打出 | ✓ 手牌单击即打出 | 能用，但语义要改（见 P1-1） |
| `accelerate` | 激奏 | ✗ `web/src` 里 0 处 | **必修**：付不起本体时唯一入口 |
| `crystallize` | 结晶 | ✗ 同上 | **必修** |
| `engage` | 启动（护符/纹章） | ✓ `doSourceAction` | — |
| `evolve` / `superevolve` | 进化 / 超进化 | ✓ 拖拽 + 面板按钮 | — |
| `fusion` | 融合 | ✓ | — |
| `use_extra_pp` | 使用额外能量点 | ✓ | — |
| `attack_leader` / `attack_entity` | 攻击（合法动作用这套词表） | ✓ 提交时合并成 `attack`（实体目标带 `defender`） | — |
| `end_turn` | 结束回合 | ✓ | — |

两条容易踩的契约：

1. **激奏/结晶与本体互斥**。引擎按官方 QA（`internal/runner/runner.go` 的
   `case "accelerate"` 注释，QA `npml0tn71d`）实现成 `激奏费用 ≤ PP < 本体费用`：
   付得起本体时只出现 `play`，付不起时才出现替身动作。所以界面**不需要**给玩家一个
   "本体还是激奏"的菜单，只要"哪个合法发哪个"。
   例：`愚劣的兵器`（10673110）本体 8 / 激奏 4 → 4~7 费只能激奏，8 费及以上只能本体。
2. **选择请求**（`pendingChoice`）候选有三类：`entity` / `leader` / `option`。
   界面已接 `entity`（`selectedInstanceIds`）与 `leader`（`selectedLeaderSides`），
   `option` 只支持**单选**（`App.tsx` 里 `choiceOption` 是单值）——`minSelections > 1`
   的模式选择会走不通。

## 二、必修（P0，都是小而确定的修复）

### P0-1 接上 `accelerate` / `crystallize`

现状：手牌"能不能点"只看 `legal("play", id) || legal("fusion", id)`（`App.tsx`
手牌 `active` 判定），于是 4~7 费时那张激奏牌在界面上是灰的、点了没反应。
引擎侧没问题：`tests/10006/batch-98-accelerate.wbotest`
（`pp 4/8` + `action { accelerate source; }`）跑 `wbo test` 全绿。

改法：加一个"这张手牌此刻哪种方式合法"的判定，本体 / 激奏 / 结晶 / 融合任一合法即算
可用；点击、拖拽落场、右键（P1-1 会引入）与详情面板按钮都走同一个入口。

验收：构造 `pp 4/8` + 手牌 10673110 的局面，卡可点、提交 `{"kind":"accelerate"}`、
场上出现 1 个自己、本体进墓场（与上面的 `.wbotest` 场景一致）。

### P0-2 卡图不全

现状（`web/src/generated/card-art.json`，生成于 9-10）：

```text
卡图索引 247 张 · 本地素材 web/public/assets/cards 434 个文件 · 引擎卡池 910 张
样例缺图：10673110（愚劣的兵器）不在索引里 → 牌桌与卡组页都无图
```

改法：用当前卡池全量重生成索引（有素材走本地、缺的给占位并列出清单），生成脚本加一句
"卡池数量变了要重跑"的检查，避免再次静默落后。

验收：随机抽 50 张卡，牌桌与卡组页都能显示图或**明确的占位**（不允许空白）。

### P0-3 可读性（"字和背景糊在一起"）

现状：`.battle-screen:before` 铺了一层 `#48504a` 的亮色放射纹理当牌桌底；手牌信息条
字号最小到 `6px`（`.hand-info>b`，折叠态），颜色贴在中灰底上。

改法：牌桌底色降噪（去掉亮纹理或压到可忽略），文字加背板/描边，字号下限提到 9–10px，
数字用等宽字体。

验收：1280×800 与 960×680 两张截图里，手牌名、费用、攻防、EP/SEP 都能读出来。

## 三、手感（P1）

### P1-1 交互模型对齐游戏

现状：手牌 `onClick` = 直接打出、`onDoubleClick` 也打出；场上 `board-card` 同时挂了
`onClick`（攻击）与 `onPointerDown`（拖拽攻击）。所以既"和游戏不一样"，又两套并存。

改成：

| 操作 | 手牌 | 场上随从 |
| --- | --- | --- |
| 拖拽 | 拖到场上 = 打出（激奏/结晶同样按合法项提交） | 拖到对手随从/主战者 = 攻击 |
| 右键 | 打出（`onContextMenu` + `preventDefault`） | 打开详情 |
| 单击 | 选中并在详情面板显示（**不再直接打出**） | 选中 |
| 双击 | 快捷打出（保留，可关） | — |

**场上删除点击攻击**，攻击只保留拖拽一条路径。

### P1-2 资源显示

现状：`.evo-pip i { display: none }` —— EP/SEP 只有图标、没有数字，看不出还剩几点。

改成：图标 + 数字（`2/2`、`1/1`），可用时高亮、用完变灰；对手侧同样显示。

### P1-3 迟钝

现状：每次操作都 `send()` → HTTP POST → 等服务端/SSE 回来才更新（没有乐观更新），
而且 `App.tsx` 是 1889 行的单组件，任何状态变化都整块重渲染。

改成：本地先落子（乐观更新），服务端回来再校正；提交期间只禁用相关那张牌，不禁用整块
界面；把 `App.tsx` 拆成 `board/`、`hand/`、`inspector/`、状态 hooks 四块。

验收：本地对局"点击 → 视觉反馈" < 50ms；拖拽过程不掉帧。

## 四、房间系统（P2，先定方案再动手）

现状（都不算 bug，是设计选择，所以先说清再改）：

- 房间存在**内存**里，进程重启即消失；**一房一局**，打完要重开（`internal/server`）。
- 邀请码只返回给**等待中的房主**；观战是另一套**只读凭据**（`/spectate`）。
- 座位凭据只存在浏览器本地（"恢复席位"靠它），换浏览器就没了。
- **单人模式**与**线上大厅**是两个入口，**牌组**在第三个页面维护。
- 线上大厅要 WBArts JWT；本地 `wbo serve` 不要求（`/api/health` 的
  `lobbyRequiresLogin`）。

三个候选方向（选一个再排期）：

| 方案 | 做什么 | 代价 |
| --- | --- | --- |
| A. 只收敛界面 | 一个「开始对局」入口 → 对手来源三选一（内置 AI / 本地房间 / 线上房间）；座位与凭据收进「我的对局」自动管理 | 前端为主，后端不动 |
| B. 连后端一起改 | 房间可恢复（落盘/重放）、支持"再开一局"复用房间、观战/教练座位成一等公民 | 要改 `internal/server`，有协议兼容问题 |
| C. 不做房间 | 牌桌只服务"单人 + bot"，线上房间交给现有桌面客户端 | 最省事，但放弃网页在线对战 |

## 五、分期与验收

| 阶段 | 内容 | 影响面 | 验收方式 |
| --- | --- | --- | --- |
| P0 | P0-1 激奏/结晶、P0-2 卡图索引、P0-3 可读性 | `web/src` | 引擎 `wbo test` 场景 + 牌桌截图 + 手工打一局 |

| P2 | 房间系统（先选 A/B/C） | `web/src`（+ 可能 `internal/server`） | 按选定方案的验收项另写 |

## 六、待定（需要产品决定，我不默认）

1. 手牌**单击**语义：选中查看（推荐）还是不做事？**双击**是否保留为快捷打出？
2. 缺卡图：走 WBArts 素材库补齐，还是先只做占位？
3. 房间系统选 A / B / C。
4. 是否给 `web/` 引入自动化界面测试（Playwright）。现在 `web/` **没有任何自动化 UI
   测试**——P0-1 这类"引擎支持、界面没接"的缺口就是这样漏掉的；引入可以，但要新依赖和
   一条 CI 步骤。
